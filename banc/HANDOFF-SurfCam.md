# Handoff SurfCam (état au v0.63)

## Contexte
- Utilisateur : dontpanic34, francophone, Pixel 10 Pro. Répondre en français, être honnête sur ce qui n'est pas testé sur le matériel.
- App Android « SurfCam » : filme des sessions de surf depuis trépied / vélo / gimbal DJI OM4, détecte surfeurs et vagues (YOLOv8n ONNX), sauvegarde des clips de vagues (5 s avant la prise de vague, 3 s après), session complète en option.
- Dépôt : `dontpanic34/Surfcam`, branche `main`, clone local habituel `/home/user/surfcam` (à recloner si nouvelle session). La CI GitHub Actions compile l'APK et le publie dans la release `debug-latest` :
  https://github.com/dontpanic34/Surfcam/releases/download/debug-latest/app-debug.apk
- **Consigne permanente** : après chaque build réussi, télécharger l'APK, vérifier (`unzip -tq` + `grep` d'une chaîne nouvelle dans les `classes*.dex`), puis l'envoyer à l'utilisateur (fichier + lien ci-dessus). Ne pas créer de PR sauf demande.
- Attente de l'utilisateur : peu de questions, il veut que les choses marchent. « Finis » = terminer le travail en cours.

(3) À l'entrée, vraies et fausses alertes sont **indiscernables** sur les mesures disponibles : vitesse 2,52 vs 2,59, part horizontale 96 vs 96, h/l 1,40 vs 1,32, confiance 0,71 vs 0,69, durée 2,9 vs 2,6 s ; seules la taille de la boîte (47 px vs 39 px) et l'étendue latérale (0,33 vs 0,20 de l'image) diffèrent un peu : il faudra la vidéo (rejets récupérés + parties de session correspondantes) pour trouver un discriminant. Mapping : `Rejet N` = N-ième `Discard` du rapport.

## Problème en cours : le gimbal « cherche » / part à côté
Analyse de deux vidéos de l'utilisateur (Drive, 13 s et 11 s, 4K HLG) : mouvements lents = main de l'utilisateur ; pivotements rapides identiques (~1,2 s, amplitude maximale) = ordres de l'appli, parfois à l'opposé du surfeur (surfeur à gauche qui file à gauche, gimbal part à droite → sort du cadre ; puis grand retour). Hypothèse : la vitesse d'anticipation est corrompue quand le gimbal est bougé à la main ou quand la cible saute d'une personne à l'autre ; corrigé en v0.61 mais **non validé sur le terrain**. Autres hypothèses non vérifiées : en mode « Que moi / Moi d'abord » sans manchon reconnu l'appli passe en recherche ; élèves dans la mousse non jugés « en vague » donc beaucoup de vagues ratées ; la recherche (balayage ±zone) ne devrait se lancer que si plus aucune personne n'est détectée.
**Prochaine étape** : l'utilisateur envoie un rapport de session + les vidéos + l'heure approximative du problème ; lire le rapport (lignes `image`, `gimbal`, `clip`, `MARQUE`) pour trancher. Méthode d'analyse vidéo utilisée : `ffmpeg` (fps=2, tonemap) pour des planches de 9 images + corrélation de phase numpy sur images grises à 10 i/s pour mesurer le pan (script type `pan.py`).
